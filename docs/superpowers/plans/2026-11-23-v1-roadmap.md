# repo-bot version 1: plans

The [design](../specs/2026-11-23-repo-bot-design.md) covers four subsystems
that can each be built and tested alone. There is one plan for each, in the
order the design sets. A plan is written when the one before it has merged,
so that it can name the real interfaces it builds on.

| Plan | Delivers | Status |
|------|----------|--------|
| 1 | Repository tooling and checks. The command framework. `/help` as a working Actions deployment. | [Written](2026-11-23-plan-1-tooling-and-command-framework.md), awaiting review |
| 2 | Tool provisioning in Actions. The PR-Agent wrapper and runner. `/pr:review` and `/pr:describe`. | Not written |
| 3 | The server deployment: container image, bounded queue, owner allow-list, read-only token for PR-Agent. | Not written |
| 4 | Releases, the image publication, and the end-to-end checklist. | Not written |

The checks the design required before planning are done. Their results are
in the [verification findings](../specs/2026-11-23-verification-findings.md).

## What each later plan must contain

These follow from the design and the findings. They are recorded here so
that they are not lost between plans.

### Plan 2

Builds on plan 1's `Command`, `CommandContext`, `ToolProvisioner`,
`TaskRunner`, and `Reporter`.

- Lockfile built from `pr-agent[github]==0.50.0`: 100 packages (findings,
  item 5).
- Provisioner: download `uv` and a standalone Python, check each against a
  committed SHA-256, install with `--require-hashes --only-binary :all:`
  into a new directory under the runner's temporary directory, with an
  allow-listed environment and a time limit (findings, item 6).
- Wrapper script: the six requirements and the fixed settings (findings,
  items 1 and 4).
- Child environment: the four variables in findings, item 7.
- LLM settings and their validation, including `https` only and rejecting
  model names that select an encoding that is not bundled (findings,
  items 2 and 7).
- Reporter additions: the size limit, mention neutralising over the whole
  text including the copied description, and the authorised commit with the
  head-moved note.
- The design's security tests that plan 1 cannot hold: allow-listed
  environments for the install and the tool; PR-Agent's effective settings;
  a run against stand-in servers with no write call and no other host; a
  hash mismatch stops the install; secrets on every failure path.
- Continuous integration: the lockfile check, and a real on-demand install
  on a hosted runner.
- Still to verify there: the items marked "Not verified" in findings, items
  1, 2, 4, and 7.

### Plan 3

- A `TaskRunner` with a bounded queue, one active run per command per pull
  request, and drain on shutdown.
- Installation tokens: one for the bot, one read-only for PR-Agent.
- The owner allow-list, required at start-up.
- Image built from the same lockfiles, non-root, read-only root filesystem,
  one in-memory temporary directory. Where PR-Agent writes bytecode and
  caches under that filesystem is not yet known (findings, item 7).
- Continuous integration: image build, Dockerfile lint, image scan, and the
  check that Actions and the image use the same lockfiles.

### Plan 4

- The release procedure, image publication with provenance and a bill of
  materials, and the end-to-end checklist.
